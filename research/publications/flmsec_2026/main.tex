\begin{abstract}
Large language model (LLM) agents process information from multiple principals
and perform externally visible actions. Existing defences primarily seek to
prevent prompt injection by improving model robustness, but such approaches
remain dependent on empirical model behaviour and adaptive attack strategies.
This paper formulates privilege escalation (PE) as the fundamental system-level
security objective: no source of influence should increase the authority of an
execution. We introduce \emph{Principal Context}, an abstraction that derives
execution authority from authenticated provenance and an organisation's
existing access-control system. Its intersection rule is maximally permissive
under the stated PE objective and monotonically loses authority as influence
accumulates, following a low-water-mark intuition analogous to classical Biba
integrity. We then present SLED (System-Level Evaluator for Defences), which
explores finite operational models under worst-case model behaviour, and SLED-V,
which provides a serialisable verification IR with solver-backed bounded model
checking and property-scoped cone-of-influence reduction. Preliminary evidence
from finite verification models shows that SLED-V detects all seeded monitor
defects with one-step counterexamples, independent checker paths agree on safe
and unsafe instances, and exploratory comparative verification suggests that
several published defence abstractions satisfy their own intended properties
while violating PE. All results are preliminary, bounded to finite models under
stated assumptions.
\end{abstract}

\section{Introduction}
\label{sec:intro}

LLM agents read documents, retrieve information, invoke tools, and perform
externally visible actions on behalf of users. Unlike traditional software,
these agents process natural-language inputs originating from multiple
principals---users, documents, databases, APIs, and other systems. Arbitrary
information may influence decisions with real-world consequences.

Prompt injection has emerged as a fundamental security challenge
\citep{rossi2024earlycategorizationpromptinjection}. An attacker may supply
crafted instructions through any input channel, causing an agent to ignore its
intended behaviour. Although progress has been made on model-level defences
\citep{struq2024,spotlighting2024}, these approaches ultimately rely on the
language model recognising or resisting malicious instructions. Because prompt
injection is inherently adaptive, such defences cannot provide stable guarantees.

This paper studies \emph{privilege escalation} (PE) as the fundamental
system-level security problem \citep{provos2003preventing}. Prompt injection is one mechanism by which PE may
occur, but it is not the only one. More generally, any information influencing
an agent may affect its subsequent behaviour. Since a system-level defence cannot
prevent arbitrary prompt injection without preventing the agent from processing
untrusted information, we focus instead on preventing any source of
influence---whether prompt injection, retrieved documents, or arbitrary model
behaviour---from increasing authority.

Under a worst-case threat model, the relevant question is not whether an input
is malicious, but whether \emph{every} principal influencing an action is
authorised to perform that action. If this property holds, arbitrary model
behaviour cannot escalate privilege regardless of how influence was obtained.

\paragraph{Motivating example.}
Consider a workflow where Alice, who is authorised to send email, requests
that the agent email a document authored by Mallory, who is not. The resulting
execution inherits influence from both Alice and Mallory. A requester-only
controller that checks only Alice's permissions would permit the action.
Principal Context includes both Alice and Mallory in the influence set; since
Mallory lacks permission, the effective authority excludes the email action.
SLED-V finds a counterexample in the requester-only model.

\paragraph{Contributions.}
\begin{enumerate}[leftmargin=*,nosep]
  \item We formulate PE as a system-level security objective for LLM agents
    operating within existing access-control systems, and define a threat model
    in which the LLM is an adversarial component
    (Section~\ref{sec:threat-model}).

  \item We introduce \emph{Principal Context}, a provenance-based enforcement
    mechanism that derives effective authority by intersecting the permissions of
    all influencing principals. We prove that this rule is maximally permissive
    under the PE objective and that authority is monotonically non-increasing as
    influence accumulates (Section~\ref{sec:ites}).

  \item We present SLED and SLED-V, which evaluate system-level defences under
    worst-case model behaviour: explicit-state exploration, a serialisable
    verification IR, solver-backed bounded model checking, and property-scoped
    cone-of-influence reduction with counterexample lifting
    (Section~\ref{sec:sled}).

  \item We provide preliminary evidence from finite verification models:
    seeded-defect detection, independent checker agreement, COI reduction, and
    exploratory comparative defence verification suggesting that published
    defence abstractions can satisfy their own properties while violating PE
    (Section~\ref{sec:evaluation}).
\end{enumerate}

\section{Threat Model and Security Objective}
\label{sec:threat-model}

We consider an LLM-based agent that performs externally visible actions on
behalf of users. The agent receives information from multiple principals, both
directly through user prompts and indirectly through documents, retrieved
content, databases, APIs, and tool outputs.

Any principal may provide arbitrary inputs. We make no assumptions about the
language model's ability to distinguish instructions from data, identify
malicious content, or resist prompt injection. Instead, we adopt a worst-case
model in which any information processed by the model may arbitrarily influence
subsequent executions. Here ``arbitrary'' means any well-typed proposal
admitted by the system interface---not malformed protocol behaviour, arbitrary
code execution, or side channels.

\subsection{Access-Control System}

We model the access-control system as the tuple $(U, A, D, P, W, R)$
\citep{servos2017abac}:
\begin{itemize}[nosep,leftmargin=*]
  \item $A$: externally visible parameterised actions
  \item $U$: principals
  \item $D$: data objects
  \item $P \subseteq U \times A$: permission relation
  \item $W \subseteq D \times U$: authorship relation
  \item $R \subseteq D \times U$: read relation
\end{itemize}

For principal $u \in U$ and action $a \in A$, $P(u,a)$ holds iff $u$ is
authorised to perform $a$. Permissions are not assumed to be hierarchical: two
principals may possess overlapping but incomparable permissions.

\subsection{Security Objective}

\begin{definition}[Influencing Principal]
\label{def:influence}
A principal $u$ influences an action if information originating from $u$
contributes, directly or indirectly, to the execution that produces the action.
The set of influencing principals for execution $e$ is denoted
$\mathrm{Influence}(e)$.
\end{definition}

\begin{definition}[Privilege Escalation]
\label{def:pe}
Privilege escalation occurs iff an action $a \in A$ is performed for which
there exists an influencing principal $u \in \mathrm{Influence}(e)$ satisfying
$\neg P(u,a)$.
\end{definition}

This formulation abstracts away the mechanism by which influence arises. Under
the stated threat model, security depends only on provenance and the permissions
assigned by the current access-control system.

\section{Principal Context and ITES}
\label{sec:ites}

We present \emph{Influence Tracking with Extrapolated Security} (ITES), a
provenance-based enforcement mechanism whose central abstraction is the
Principal Context. ITES derives execution authority from authenticated
provenance and an organisation's existing access-control system.

\subsection{Influence Tracking}

Every execution inherits the authority implied by the provenance of its inputs.
The initial influence set of execution $e$ with inputs $ds \subseteq D$ is:
\[
\mathrm{Influence}(e) = \bigcup_{d \in ds} \{u \in U \mid W(d,u)\}
\]
Every object produced by an execution inherits the complete influence set of
that execution. Influence therefore accumulates monotonically: once a principal
has influenced a computation, that influence persists unless a trusted
provenance mechanism establishes otherwise.

\subsection{Authorisation}

Given execution $e$ with influence set $I = \mathrm{Influence}(e)$, the
authorisation rule permits action $a \in A$ iff:
\[
\mathrm{Allow}(I, a) \iff I \neq \varnothing \;\land\; \forall u \in I,\; P(u,a)
\]
The non-empty condition prevents vacuous authority from an empty context. The
effective authority is:
\[
\mathrm{Permitted}(I) = \bigcap_{u \in I} \{a \in A \mid P(u,a)\}
\]

\subsection{Maximal Secure Authorisation}

\begin{theorem}[Maximal Secure Authorisation]
\label{thm:maximal}
The intersection rule authorises the maximal set of actions that can be
permitted without allowing privilege escalation.
\end{theorem}

\begin{proof}
ITES authorises exactly $\mathrm{Permitted}(I)$. Suppose an alternative rule
permits a strict superset. Then there exists $a \notin
\mathrm{Permitted}(I)$ that the alternative permits. Since $a \notin
\mathrm{Permitted}(I)$, there exists $u \in I$ with $\neg P(u,a)$. Executing
$a$ satisfies Definition~\ref{def:pe}. Hence any strict superset permits PE.
\end{proof}

\subsection{Authority Monotonicity}

\begin{theorem}[Authority Monotonicity]
\label{thm:monotonicity}
For a fixed ACS state, if $\mathrm{Influence}(e_1) \subseteq
\mathrm{Influence}(e_2)$, then
$\mathrm{Permitted}(\mathrm{Influence}(e_2)) \subseteq
\mathrm{Permitted}(\mathrm{Influence}(e_1))$.
\end{theorem}

\begin{proof}
Adding influencing principals introduces additional intersections. The
resulting permission set can only remain unchanged or decrease.
\end{proof}

\paragraph{Relationship to classical integrity.}
Principal Context follows a \emph{low-water-mark} intuition: incorporating
additional, potentially lower-authority influence cannot increase effective
authority. This is structurally analogous to Biba's low-water-mark integrity
policy \citep{biba1977}, operationalised in systems such as LOMAC
\citep{lomac2001}. The similarity is structural rather than an equivalence of
policy models. Low-water-mark integrity lowers a subject's effective integrity
after consuming lower-integrity information. Principal Context instead retains
the identities of all conservatively influencing principals and computes
permitted parameterised actions from the intersection of their current ACS
permissions. Attenuation is induced by organisational authority rather than by
assigning a single integrity label to the execution. When permission sets are
ordered by inclusion, intersection is their meet \citep{denning1976}.

\subsection{Security Guarantee}

\begin{corollary}
\label{cor:pe-prevention}
Under the threat model of Section~\ref{sec:threat-model}, and assuming correct
enforcement of influence tracking, provenance, and access-control checks,
Principal Context prevents privilege escalation.
\end{corollary}

\begin{proof}
By Theorem~\ref{thm:maximal}, only non-PE actions are permitted. By
Definition~\ref{def:pe}, privilege escalation requires an influencing principal
lacking permission. Such a principal cannot exist if the action is permitted.
\end{proof}

This guarantee is independent of the source of influence. Prompt injection,
retrieved documents, compromised tools, and arbitrary model behaviour are
treated uniformly: once information contributes to an execution, the authority
of that execution is constrained by the permissions of the corresponding
principals.

\section{SLED and SLED-V}
\label{sec:sled}

Existing prompt-injection benchmarks evaluate robustness against a finite
collection of attacks \citep{agentdojo2024}. Such evaluations are necessarily
incomplete: passing a benchmark demonstrates robustness only against the attacks
it contains. We instead evaluate whether a system-level defence correctly
enforces its intended security properties regardless of model behaviour.

\subsection{SLED: Explicit-State Exploration}

SLED (System-Level Evaluator for Defences) treats the language model as an
adversarial component. Rather than executing a particular model, each execution
is a nondeterministic black box that may produce any well-typed proposal
consistent with the system interface.

Beginning from an initial state, SLED enumerates every action that may result
from each pending execution under worst-case assumptions. Exploration
continues until every reachable state has been visited or a configured bound is
reached. The resulting state-transition system covers every reachable state
under the configured proposal model; predecessor edges retain counterexample
paths.

SLED reports four verdicts:
\begin{description}[nosep,leftmargin=*]
\item[\textsc{SAFE}] The finite reachable state space was exhausted without
violation.
\item[\textsc{Bounded\_Safe}] No violation was found, but a configured bound
truncated work.
\item[\textsc{UNSAFE}] A safety property failed with a counterexample.
\item[\textsc{UNKNOWN}] Modelling, property, or adapter evaluation failed.
\end{description}

Depth, state, transition, and model-call bounds are explicit.
\textsc{SAFE} is reserved for an exhausted finite state space; bounded results
are never silently promoted to proof.

\subsection{SLED-V: Verification IR and Solver-Backed Checking}

SLED-V is an exploratory verification methodology that accepts a finite
serialisable transition IR rather than arbitrary Python.
The IR is a standalone representation with variables, transition rules, and
invariants that can be checked by:

\begin{enumerate}[nosep,leftmargin=*]
  \item A \emph{reference interpreter} that exhaustively explores the state
    space.
  \item \emph{Z3 bounded model checking} (BMC) for solver-backed verification.
  \item A \emph{nuXmv} subset adapter (returns \textsc{UNKNOWN} when the binary
    is unavailable).
\end{enumerate}

Properties currently supported include: unauthorised execution, forbidden
observation, provenance monotonicity, branch isolation, and bounded resource
use. Observational confidentiality is checked via IR self-composition
\citep{barthe2004self}: the IR is doubled into a product system with primed
variable copies, confidentiality invariants assert
$\text{observable} = \text{observable}'$, and existing backends verify the
product. This produces bounded evidence, not a noninterference proof
\citep{goguen1982,sabelfeld2003}.

\subsection{Cone-of-Influence Reduction}

Property-scoped cone-of-influence (COI) reduction closes transitively over
guards and right-hand-side dependencies that may update an invariant variable.
Reduction is accepted only when:

\begin{enumerate}[nosep,leftmargin=*]
  \item Original and reduced reference verdicts agree.
  \item Rule identifiers are stable for witness replay.
  \item An unsafe witness lifts to the original model.
\end{enumerate}

A smaller model alone is not evidence of preservation; explicit comparison is
required.

\subsection{Counterexample Reconstruction}

Every \textsc{UNSAFE} result includes a counterexample: a sequence of
transitions from the initial state to a bad state. COI reduction preserves rule
identifiers so that a reduced witness can be projected back to the original
model. If the witness cannot be lifted, the comparison fails.

\subsection{Runtime-to-IR Boundary}

The IR is a hand-written abstraction of the runtime kernel, not a translation
of arbitrary Python. The runtime kernel and the IR share the same canonical
transition semantics, but formal equivalence is not claimed. Differential
conformance testing---comparing runtime and IR decisions on equivalent
states---is a future direction.

\section{Evaluation}
\label{sec:evaluation}

The following evaluation reports \emph{preliminary evidence} from finite
verification models. These results are exploratory: they demonstrate the
methodology's capability on small finite models, not deployment-level
guarantees. Their significance lies in showing that SLED-V can distinguish
safe from defective defences, that independent checkers agree, that COI
reduction preserves verdicts, and that property-relative comparison can
reveal privilege-escalation gaps in defence abstractions that satisfy their
own intended properties. All results are bounded to finite models under stated
bounds and assumptions; no unbounded or deployment-level security claim is
made. Further validation on larger models and with additional solver backends
is needed before broader conclusions can be drawn.

We evaluate SLED-V through four research questions:

\begin{description}[nosep,leftmargin=*]
\item[\textbf{RQ1}] Can SLED-V reliably distinguish safe and defective finite
models of system-level agent defences?
\item[\textbf{RQ2}] Do independent verification paths agree on safe and unsafe
instances?
\item[\textbf{RQ3}] Can property-scoped COI reduce verification models without
changing verdicts or losing counterexamples?
\item[\textbf{RQ4}] What does property-relative verification reveal when
comparing Principal Context with other system-level defence abstractions?
\end{description}

\subsection{RQ1: Seeded-Defect Detection}

Table~\ref{tab:defect-detection} shows that SLED-V's native explicit-state
exploration detects all five seeded defective monitors, each with a one-step
counterexample. The canonical ITES model exhausts \textsc{SAFE} within the
checked bounds. An additional 11 direction-readiness mutants (7 delegation, 4
disclosure) are similarly detected with one-step witnesses.

was designed for while failing a different system-level security property. This
is a \emph{model-level} comparison of explicit finite abstractions, not an
implementation-level evaluation of the published systems.

\section{Related Work}
\label{sec:related}

\paragraph{Classical integrity and information-flow control.}
Biba \citep{biba1977} defines integrity policies including low-water-mark
variants where consuming lower-integrity information reduces a subject's
effective integrity. LOMAC \citep{lomac2001} operationalises this in commodity
operating systems. Denning \citep{denning1976} provides the lattice model for
secure information flow; Principal Context's authority intersection is a meet
in the powerset lattice over permission sets. Goguen and Meseguer
\citep{goguen1982} establish noninterference, which is strictly stronger than
the access-safety properties verified here. Sabelfeld and Myers
\citep{sabelfeld2003} provide vocabulary for explicit and implicit flows;
Myers and Liskov \citep{myers1997difc} introduce decentralized IFC.
Principal Context conservatively assumes that if information from a principal
reaches an execution, that principal may influence its output---an intentional
overapproximation, not a claim of exact causal dependence.

\paragraph{System-level LLM-agent defences.}
The Dual-LLM pattern \citep{beurerkellner2025designpatternssecuringllm} separates
a privileged planning model from a quarantined data-processing model. CaMeL
\citep{debenedetti2025defeatingpromptinjectionsdesign} extends this with
capability tracking and developer-defined policies enforced by a custom
interpreter. Progent \citep{progent2025} mediates tool calls with symbolic
privilege-control policies. PACT \citep{pact2026} tracks argument-level
provenance. FORGE \citep{forge2026} enforces history-sensitive Datalog policies.
Each optimises for a different security objective; our comparative verification
(Section~\ref{sec:evaluation}) shows that satisfying a defence-native property
does not imply PE safety. Wu et al.\ \citep{wu2024systemleveldefenseindirectprompt}
study prompt injection from an information-flow perspective.

\paragraph{Evaluation.}
AgentDojo \citep{agentdojo2024} provides realistic prompt-injection tasks and
metrics. We treat such benchmarks as complementary empirical evaluation: they
test finite attack/defence combinations, while SLED-V evaluates whether a defence
satisfies its intended property under arbitrary model behaviour. An
AgentDojo integration pipeline executes end-to-end with a small model, but
utility is too low for efficacy claims; this is integration evidence, not a
headline result.

\section{Discussion}
\label{sec:discussion}

\paragraph{Security--utility frontier.}
Under fixed permissions $P$ and the PE objective, the intersection rule is
maximal (Theorem~\ref{thm:maximal}). Recovering more utility requires changing
authority or policy: explicit delegation (modelled as an ACS transition),
trusted declassification/endorsement, or a different security objective. This
is a fundamental trade-off, not an implementation limitation.

\paragraph{Delegation, consent, and authority-bearing arguments.}
The PE objective as stated treats all influence uniformly. In practice,
organisations need delegation (one principal authorising another to act),
consent (a principal agreeing to an action affecting their data), and
authority-bearing arguments (an argument whose provenance grants elevated
permission). Our implementation models these as ACS state transitions---e.g.,
a delegation grant updates $P$ for a bounded scope and duration---so that
the PE property is preserved under the updated ACS state. The seeded
delegation and disclosure mutants in Table~\ref{tab:defect-detection}
demonstrate that SLED-V detects defective delegation and disclosure monitors
under this model. A formal treatment of authority-bearing arguments and
consent as first-class security decisions is left to future work.

\paragraph{Model-level vs.\ system-level.}
Model-level defences and system-level enforcement are complementary. Model
robustness can improve utility by producing better proposals, while
authorization security is enforced at the system boundary. A stronger model
does not weaken the security argument because the model is assumed adversarial.

\paragraph{Limitations.}
Results are preliminary and bounded to finite models (Section~\ref{sec:evaluation}).
The trusted computing base is specified in Section~\ref{sec:threat-model}; in
particular, the verified IR is a hand-written abstraction of the runtime kernel
and formal equivalence is not claimed. Observational confidentiality evidence
is bounded and does not constitute a noninterference proof. Comparative defence
results are model-level comparisons of explicit finite abstractions, not
implementation-level evaluations of the published systems.

%% ------------------------------------------------------------------
\section{Conclusion}
\label{sec:conclusion}

We have argued that privilege escalation, rather than prompt injection itself,
is the appropriate system-level security objective for LLM agents. Principal
Context derives execution authority from authenticated provenance and an
organisation's existing access-control system; its intersection rule is
maximally permissive under the PE objective and monotonically loses authority
as influence accumulates. SLED and SLED-V provide preliminary finite-state and
solver-backed evidence that implementations enforce the resulting properties,
detecting defective monitors with minimal counterexamples and suggesting that
satisfying a defence-native property does not imply PE safety. All results are
preliminary and bounded to finite models under stated assumptions; further
validation is needed before broader claims can be made.
