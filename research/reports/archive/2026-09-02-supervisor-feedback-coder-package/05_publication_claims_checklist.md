# Publication Claim-Level Checklist

## Core ITES claims

[ ] Define PE as an action performed beyond the authority of at least one influencing principal.

[ ] Define Principal Context precisely.

[ ] State that provenance correctness/authentication is part of the trusted computing base/assumption.

[ ] State that authenticated provenance improves attribution accuracy but does not grant authority.

[ ] State that genuine low-authority influence intentionally reduces the allowed action set.

[ ] State that the ACS itself is assumed correct and is not secured by ITES.

[ ] State that ITES does not guarantee user intent or prevent misuse of authority already held.

[ ] Replace broad "maximal utility" claims with precise maximal-permissiveness language.

## Classical lineage

[ ] For each comparison, state the native security objective and influence granularity.

## CaMeL-specific constraints

[ ] Acknowledge Python policy programmability.

[ ] Acknowledge provenance/capability tracking.

[ ] Acknowledge STRICT dependency propagation/control-flow treatment.

[ ] Do not claim "cannot express PE".

[ ] Do not claim "satisfies PE if one writes a policy" without explaining the missing principal/ACS/influence semantics.

[ ] Phrase the result as a native-guarantee/non-implication comparison.

## SLED/SLED-V claims

[ ] Distinguish evaluator generality from ITES conformance testing.

[ ] State finite bounds explicitly.

[ ] Distinguish raw traces, canonical states, and excluded/incomplete runs.

[ ] Do not present bounded evidence as proof of unbounded correctness.

[ ] State whether a result is a theorem, model-checking result, conformance result, or empirical benchmark result.

## Utility and planning

[ ] Include external-email/calendar worked example.

[ ] Explain utility loss from genuine external influence.

[ ] Explain utility recovery through fine-grained provenance.

[ ] Explain utility recovery through ordering/isolation of subtasks.

[ ] Explain protected planning as empirical utility/robustness improvement under attack.

[ ] Keep planning from silently removing real provenance/influence.

## Persistent influence / laundering

[ ] Persist Principal Context through derived artefacts.

[ ] Persist influence through scheduling.

[ ] Test cross-assistant-call and cross-session laundering.

[ ] Separate trusted transformation/delegation from ordinary model execution.
